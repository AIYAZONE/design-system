## 三、业务分类：让应用入口可理解

### 业务应用层

应用按使用人群与完整任务分类，不按站点数量分类：

| 应用 | 面向谁、完成什么 | 主要下层能力 |
| --- | --- | --- |
| 品牌与内容门户 | 访客了解品牌、阅读文章、查询产品资料 | 内容、站点、搜索、SEO |
| 电商店面 | 买家浏览商品、购物车、进入结账 | 商品查询、购物车、Shopify 交易能力 |
| 营销活动中心 | 访客参加活动、提交线索；运营投放活动 | 内容、活动规则、表单、同意管理、归因 |
| 会员中心 | 用户登录、查看资料、权益与订单入口 | 消费者身份、客户资料、会员、订单查询适配 |
| 帮助与售后门户 | 用户检索帮助、提交问题、查看服务进度 | 知识内容、搜索、客服工单与外部服务 |
| 运营工作台 | 运营管理品牌站点、页面、素材、预览和发布 | Atlas Admin/Builder、权限、站点与发布 |

后面三个应用的完整会员、工单和营销规则能力是候选；不因为原图出现“账户与支持”就标为实现。

页面类型属于应用内部：主页、商品详情、集合页、文章、落地页、帮助页、账户页、购物车等。桌面/手机属于渠道。站点、品牌、语言、区域属于装配和隔离维度。

### 多站点的具体含义

同一平台管理多个独立访问入口，每个入口有自己的域名、内容、主题、语言/币种、店铺绑定、发布版本与区域归属。例如“品牌 A 的欧洲店面”和“品牌 A 的日本店面”是两个站点，可以复用电商应用和主题，但有不同的配置与数据边界。

推荐实体关系：组织 → 品牌 → 站点；站点关联区域、域名、语言集、店铺、主题版本与能力配置。站点不是组织租户，也不是区域数据库的同义词。

当前代码主要以 site code 管理站点；集团组织、品牌模型、区域归属和授权隔离属于目标扩展。图中“站点管理”位于领域层，点击后展示上述例子与关系，而非在应用层放一个模糊“多站点”框。

七层是阅读结构。业务请求可能直接访问静态 CDN，不必依次经过每层；源代码依赖也不等于图的上下顺序。默认图应用在上、基础设施在下，层号从底向上递增。

| 层 | 解决的问题 | 必须呈现的模块与功能 |
| --- | --- | --- |
| L7 业务应用 | 谁完成什么业务任务 | 六个应用，采用第三节的名称和边界 |
| L6 体验与呈现 | 数据如何变成可交互界面 | 管理 UI（Admin/Builder 与共享壳）；站点渲染（Runtime、Schema 校验、Registry、Theme 装配、SSR/SSG、未知组件回退）；ZDS（令牌、十组件、图标、国际化、工具）；业务组合（稳定复用的营销/表单/展示模式）；客户端接入（API 客户端、站点路由、状态、表单与错误提示） |

| L4 应用用例与流程 | 一次业务任务如何编排 | 内容管理用例（建页、草稿、复制、素材与全局块同步）；发布预览流程（校验、版本固定、构建、上线、回滚）；交易用例（商品查询、购物车、结账跳转）；客户服务用例（会员查询、权益与工单适配）；营销用例（活动、线索、同意与归因）；异步任务（排队、状态、重试、补偿、定时任务） |
| L3 领域能力 | 核心规则与数据由谁负责 | 组织品牌与站点（归属、域名、店铺、语言/区域配置）；内容与素材（模型、页面、版本、全局区块、素材引用）；发布版本（发布清单、线上指针、不可变产物）；商业能力边界（商品、价格、库存、购物车、订单/支付/履约由 Shopify 承担，平台只适配）；消费者与会员（身份关联、资料、权益，候选）；营销与客服（活动、线索、知识与工单，候选） |
| L2 数据与技术适配 | 如何实现持久化及连接外部系统 | 关系存储适配（领域 Repository、事务、迁移、索引、站点隔离）；对象存储适配（素材/产物、版本与签名访问）；缓存与搜索（缓存一致性、索引投影，按需候选）；消息任务适配（队列、Outbox、消费者去重、死信，候选）；外部系统适配（Shopify、身份、CRM/ERP/仓储、通知）；分析数据管道（事件归集、区域汇总、报表投影，候选） |
| L1 运行基础设施 | 能力在哪里运行、如何恢复 | 区域网络与边缘（DNS、CDN、WAF、负载均衡、私网）；计算（Java API、Node Preview、Publisher Worker、Nuxt 运行单元）；数据库资源（区域 PostgreSQL/Supabase、连接池、备份）；对象与队列资源（S3、可选缓存/消息资源）；运维基础（密钥、配置、IaC、健康检查、扩缩容与灾备） |

横切治理作为侧边支撑带：

- 身份与安全：管理 IAM 与消费者身份分开；RBAC、组织/站点授权、秘密管理、同意与审计。
- 工程交付：Java/Node 构建隔离，Schema/API 兼容，组件包版本，CI、产物溯源和部署回退。
- 可观测性与可靠性：日志、指标、Trace、RUM、错误预算、告警、容量、故障恢复。
- 数据与架构治理：数据所有者、生命周期、区域驻留、契约版本、依赖门禁、决策与责任角色。

以上各行的模块成为可选择节点；括号内子能力在详情与完整清单展开。首屏不把所有功能文字塞进图，也不为追求数量把每个功能都画成服务。

## 五、依赖规则：代码、调用、数据分开表达

### 目标代码依赖矩阵

| 源模块 | 可依赖 | 禁止或需经契约替代 |
| --- | --- | --- |
| 应用 UI | 体验组件、客户端、公开 DTO/Schema | 数据库驱动、管理密钥、其他应用内部实现 |
| ZDS 基础包 | 令牌、通用工具、声明的基础运行依赖 | Atlas、会员、Shopify、业务页面 |
| 业务组合 | ZDS、稳定的展示契约 | 直接操作后端数据库；反向要求 ZDS 依赖组合 |
| Builder/Admin | 客户端、Schema、共享管理 UI | import Storefront 真正 Renderer 或 Theme；借 iframe 跨越服务权限 |
| Preview/Publisher/Web | Runtime、Schema、Theme/能力装配、客户端端口 | Builder/Admin 内部代码 |
| API 适配 | 应用用例、输入输出契约 | 领域依赖 Controller、把公开 DTO 当持久化实体 |
| 应用用例 | 领域规则、Repository/集成端口、事件契约 | 直接依赖具体云 SDK 或跨领域表 |
| 领域 | 自身模型、规则、必要的纯共享类型 | HTTP、Controller、ORM、AWS、Shopify SDK、其他域的 Repository |
| 基础设施适配 | 领域/应用声明的端口与外部 SDK | 其他域私有数据结构或绕开用例的业务决策 |
| 启动装配 | 用例、适配、运行配置 | 向领域层反向注入容器与框架依赖 |

运行时是“用例调用端口，具体适配执行存储/远程请求”；源码依赖是“适配实现内层定义的端口”。因此不画成“领域 import 数据库 SDK”。

当前 Java 的 domain 使用持久化实体，Service 直接引用 Repository；目标端口与适配分离展示为待演进，不伪称当前已完成 Clean Architecture。当前 Atlas 内部相对路径导入也保留为现状说明。

跨领域采用公开查询接口、命令或事件。统一部署的模块允许进程内调用，但仍不能跨域读写私有表。静态展示业务组件可以直接使用 ZDS，不强制经过空的组合层。

### 运行调用关系

六个场景由统一关系数据生成：

1. **访客访问**：浏览器 → CDN → 已发布静态产物；动态商品/购物车 → 区域公共 API → 商业用例 → Shopify 适配 → Shopify。
2. **编辑与预览**：运营 → Admin/Builder → 管理 API → 内容用例/区域库；预览 → Java 接入 → Node Preview → Runtime/Theme，并按需要通过 API 读取内容与商品。
3. **内容发布**：运营 → 发布用例 → 发布任务 → Worker → 固定版本内容/Runtime → 产物存储 → 发布指针/边缘生效。当前同步代码与目标异步流程分别绘图。
4. **消费者账户**：会员中心 → 消费者身份/客户 API → 会员域及订单查询适配；未建设环节全部标为候选，不接 Atlas 管理账户充数。
5. **外部事件与分析**：外部系统 → Webhook 接入 → 去重/队列 → 领域处理或区域分析投影 → 允许共享的聚合报表。
6. **组件与 AI 交付**：源码 → CEM/清单/API 文档 → 人与 AI；包构建/检查 → 制品 → 应用构建 → 部署。包依赖不画成线上后端调用。

“全部概览”只显示主关系及横切作用。选择场景或模块显示相关连线，其他模块仍可见；标识同步请求、事件、代码依赖与产物交付四种关系。

## 六、关键目标契约与发布一致性

此节是新增目标设计，不是已有接口声明。现有接口另存证据：
`/api/sites`、`/api/site-stores`、`/api/pages`、页面 `versions/publish/rollback/preview-render`、`/api/assets`、`/api/global-sections`、`/api/site-stores/{siteCode}/products` 与 `cart`、`/preview/{pageId}`。

### 目标契约

| 契约 | 输入 | 输出、失败与边界 |
| --- | --- | --- |
| 解析站点上下文 | 已验证 Host、访问区域、语言偏好 | `orgId/brandId/siteId/homeRegion/storeRef/locale/configVersion`；未知 Host 拒绝，不靠客户端 siteId 建立授权 |
| 保存内容草稿 | 主体权限、siteId、pageId、baseRevision、Schema 版本、内容 | 新 revision；并发冲突返回冲突状态；校验失败返回字段路径，不覆盖别人草稿 |
| 提交发布 | 固定 contentVersion、themeVersion、runtimeVersion、configVersion、幂等键 | `releaseId/jobId/status`；建议异步接受；同键同请求返回同任务，同键异参拒绝 |
| 查询发布任务 | releaseId、授权站点 | queued/building/validating/activating/succeeded/failed/cancelled 状态、失败阶段与产物信息 |
| 激活发布 | releaseId、预期 currentReleaseId、产物校验结果 | 比较并交换线上指针；冲突重新评审；失败保留旧版本 |
| 回滚发布 | 目标已成功 releaseId、预期当前指针、原因 | 复用完整历史版本及产物，记录审计；与源码当前“仅内容指针回滚”明确区分 |
| 交易适配 | siteId、映射店铺、商品/购物车操作、用户上下文 | 稳定公开视图与 Shopify checkout 地址；受控超时、429、失效购物车；不复制支付权威状态 |
| 接收外部事件 | provider、eventId、签名、时间戳、区域映射 | 验签、持久接收后确认；重复幂等；业务处理失败进入重试/死信 |

事件信封：`eventId/type/schemaVersion/occurredAt/orgId/siteId/region/correlationId/aggregateId/aggregateVersion/data`。主体事件候选为 `ContentVersionCreated`、`ReleaseRequested`、`ReleaseActivated`、`ReleaseFailed`、`CommerceEventReceived`、`CustomerConsentChanged`。

事件默认至少一次投递，消费者按 eventId 去重；同一聚合按版本检测乱序。只发送必要信息，不携带密钥或支付敏感数据。事务内 Outbox 确保数据库提交与待发送记录一致；没有跨系统全局事务承诺。

### 安全发布目标

1. 固定内容、主题、Runtime、配置四个版本，创建发布记录与 Outbox。
2. Worker 按 releaseId 幂等构建；每站点激活串行，不同站点并行且配额隔离。
3. 写入不可变 `siteId/releaseId` 产物前缀，检查清单、摘要、链接及可访问性。
4. 产物就绪后，通过条件更新激活发布记录；边缘路由切换为单独可观测步骤。
5. CDN 生效受传播时间影响；在确认前状态为 activating，不提前报告全部成功。
6. 构建、上传或校验失败保持原发布；切换失败记录补偿/重试，保留旧产物。
7. 回滚复用历史 release；内容基线与编辑草稿如何处理显式记录，不能默默清除未发布改动。

页面展示“目标机制”和“现状缺口”，本次不实现队列、Outbox 或发布重构。

## 七、数据所有权与区域部署

### 数据归属

| 数据 | 权威所有者 | 存储与共享策略 |
| --- | --- | --- |
| 组织、品牌、站点归属及域名 | 平台站点域，组织品牌部分为候选 | 管理控制面；全球只读配置副本，版本化 |
| 页面、素材引用、Schema 与内容版本 | Atlas 内容域 | 所属区域 PostgreSQL；公共内容可按发布规则分发 |
| 发布记录、线上指针、构建清单 | 发布域，完整 release 模型为候选 | 区域库 + 对象存储；产物不可变，可 CDN 分发 |
| 商品、价格、库存、客户、订单、支付、履约 | Shopify 或已确认外部系统 | 平台持有映射与必要缓存/投影，不成为第二真相源 |
| 消费者凭证、身份关联与会员权益 | 消费者身份提供方/会员域，待建设 | 所属区域；集团管理员 IAM 独立 |
| 线索、同意、工单、个人行为事件 | 对应营销/客服/隐私域，候选 | 区域驻留；跨区仅允许的脱敏/汇总数据 |
| 搜索索引、报表、缓存 | 投影所有者 | 可重建，不允许反向写主数据 |

目标所有业务记录带组织/站点归属；服务端从可信身份与站点注册表解析权限。连接池共享场景不能只靠不可靠的会话变量实现隔离；Repository 查询约束与可验证的数据库策略共同保障。当前存在 site 字段不等于完整多租户隔离。

### 部署边界

- 全球控制面：非敏感站点注册、公开配置版本、制品索引与允许共享的汇总；管理者身份与审计仍按实际驻留要求布置。
- 区域业务面：区域 API、管理/消费者接入、内容库、发布任务与对象存储、集成适配、区域分析。
- CDN 边缘：公开静态内容与资源；个人数据 API 不使用公共缓存。
- Java：现有内容、站点、素材、版本等先保持模块化部署；消费者身份和重负载集成按独立生命周期拆分。
- Node Preview：交互预览单独伸缩；Publisher Worker：CPU/IO 密集构建单独队列伸缩，避免影响编辑 API。
- Nuxt：管理应用保留现有栈；站点根据现有 Web 与 SSG/SSR 模式展示，未验证的生产 SSR 标为目标。
- 持久资源：区域 PostgreSQL/Supabase、S3；消息优先建议托管队列与死信，缓存与独立搜索按容量触发，不默认引入 Kafka、服务网格或 Kubernetes。
- 计算蓝图建议使用 AWS 托管容器服务承接 Java/Node；实际平台未核实，页面必须显示“部署建议”，不能画成已在运行。
- local/dev/staging/prod 分开实例/命名空间、凭证与存储；跨区容灾不自动复制个人数据到未经允许区域。

区域写入路由以 homeRegion 为准。跨区误路由返回可重试路由提示；所属区域不可用时不自动在另一地区创建同一实体写主库。允许的灾备区域、保留期与法律依据进入上线前决策项。
