# 架构页简化验收

用户反馈：页面太复杂。默认入口改为「业务应用 → 平台能力 → 技术底座」三段总览，六类应用说明用途；底部用简短例子解释多站点及 Atlas / ZDS / Shopify 职责。

随后用户追加反馈：“这个页面的信息超多，只展示必要的信息吧”。据此把仓库实现、检查配置、平台边界、优化进度与完整功能清单从默认页拆到独立页面 `architecture-reference.html`；默认页只保留 header 与三段总览，底部给出指向资料页的链接。数据与技术蓝图沿用，简化的是展示层级与承载页面。

再追加反馈：“为什么这种架构图 我怎么看不懂啊 感觉就是大量专业术语堆叠，特别是 details 这里面”。据此对详情与三段总览做可读性改写，不改数据与结论：

| 原说法 | 现说法 |
| --- | --- |
| 依赖与调用 / 数据归属 / 区域部署 / 设计与验证 | 谁调用谁 / 数据存在哪 / 跑在哪里 / 做到哪一步 |
| 关系类型、设计视角、场景 | 看哪种关系、看哪一版、业务场景 |
| 目标蓝图、源码现状 | 打算怎么做、现在怎么做 |
| code / call / event / artifact | 代码依赖（代码里引用了对方）、同步调用（发出请求并等结果）、事件（异步通知，不等结果）、产物交付（文件或安装包） |
| 横切治理、贯穿所有层 | 通用规则、每一层都要遵守 |
| 数据所有者也即权威所有者 / 存储与区域策略 / 生命周期 | 谁说了算 / 存在哪里 / 谁能读、谁能写 / 什么时候清理 |
| 输入输出与失败契约、数据所有权与读写 | 对外接口：输入、输出、失败怎么办；涉及的数据：谁负责、存在哪 |
| 可靠性分级建议（P95 / RPO / RTO） | 可靠性建议目标，并在开头解释 P95、RPO、RTO 的含义 |
| 演进顺序与兼容 | 推进顺序与兼容 |

每个视图与模块详情顶部新增浅色导读面板（这是什么 / 为什么重要）。`<details>` 内原本还有一段“这是什么 / 怎么读 / 三个状态词”的导读，用户反馈“没必要”后删除，只保留分层全景上方一行状态词说明（源码已有 / 部分已有 / 候选设计各是什么意思）。

| 检查 | 结果 |
| --- | --- |
| 桌面 1440×900、平板 768×1024、手机 390×844 | 开发与生产均通过；没有横向溢出或页面运行错误 |
| 默认入口 `architecture.html` | 只有 header + 三段总览；已无仓库资料与功能清单节点；底部链接指向 `/architecture-reference.html` |
| 资料页 `architecture-reference.html` | 承载仓库构建关系（浅色面板）、检查配置、平台边界、优化进度与完整功能清单；导航高亮归入“架构” |
| 原生键盘及返回 | Enter 展开；阅读详情、返回模块、收起后焦点正确 |
| 五视图 | 均可切换，完整模块仍可查阅 |
| URL | 视图/模块深链接自动展开；旧 current/improvements 锚点可访问；未知地址回退总览 |
| 收起与刷新 | 收起清理详细视图 URL；重载仍展示简明入口 |
| 工程检查 | 架构数据校验（43 模块 / 217 功能 / 92 关系 / 六场景）、TypeScript/Vite、仓库 lint、改动文件显式 lint、整站组装通过 |
| 可读性改写后复验 | 详情展开、五个视图、关系控件、模块详情（导读 + 「细节」分节）均正常；导读面板底色 #f5f8fc；三尺寸 `scrollWidth === clientWidth`，无横向溢出 |
