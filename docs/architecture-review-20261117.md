# 架构现状与优化建议

核查日期：2026-11-17。范围：当前工作区源码、包声明、构建配置、GitHub 工作流和本地构建目录。没有核实内网 GitLab/Jenkins、远端分支保护、npm 已发布包或业务站点的运行配置。

本文件前半部分保留初次核查与第一批实施记录。关于 Atlas“仍是规划”的旧结论已由文末“全栈架构全景修订”纠正：同级 Atlas 项目已有实现，平台生产能力仍需独立证据。

当前组件、样式、文档分开的方向可以保留。最需要优化的是对外包接口和实际产物的一致性，其次是运行依赖、发布验证与构建流程。Atlas、多站点运行和监控属于更大的前端规划，不能用本组件仓库的成熟度代替整个业务平台的状态。

## 初次核查发现与优化优先级

本节保留实施前的证据与建议。用户随后授权继续实施，当前完成情况见文末“第一批实施结果”；本节提及的包产物缺失、CI 缺少 lint 和重复构建已在本批修复。

### P1：修正基础包声明与产物的差距

[core/package.json](../packages/core/package.json) 的 `exports` 声明了 `./button` 等组件子路径、`dist/index.d.ts` 以及组件子路径的类型文件和样式入口。[core/vite.config.ts](../packages/core/vite.config.ts) 当前仅构建 `src/index.ts` 一个入口，没有声明文件生成步骤。核查本地 `packages/core/dist` 时仅有 `index.js` 和 `index.cjs`，没有声明的组件子目录、类型文件或样式目录。源码有 dropdown 的导出，但 package exports 也没有相应子路径。

这意味着“源码里能用”不能证明“发布后按包接口能用”。门户使用源码别名也会绕过这类问题。

建议选择一个明确契约：

- 如果提供按组件导入：添加真实多入口构建、声明文件生成和实际样式输出，逐条校验 exports 对应的文件。
- 如果当前只支持总入口：先缩小声明范围，文档同步说明；但移除已承诺的公共路径需要兼容评估和合适的版本发布。

验收使用 `pnpm pack` 产物安装到不带工作区源码别名的临时消费者项目，检查 ESM/CJS、TypeScript、组件注册和主题样式。这里指出的是当前源码与本地产物的差距，未验证 npm 历史版本。

### P1：统一 npm 与 CDN 的运行依赖策略

[根 Vite 配置](../vite.config.js) 的 library 模式 `external: []` 将 Lit 等依赖打入总包；[core 配置](../packages/core/vite.config.ts) 又将 Lit 外置。开发、工作区基础包、总包和 CDN 组合接入时，可能走不同运行副本。

此次门户开发预览曾出现 `_$initialize` 初始化错误，已通过门户使用工作区源码并排除对应依赖预打包修复。这是本地预览的修复，不代表所有消费者的接入方式已经统一，也不能据此断言现网存在相同错误。

建议 npm 提供清晰的依赖契约，统一依赖版本与注册行为；CDN 可以保留自包含产物，但必须有独立且明确的入口。评估 Lit 的依赖/peerDependency 策略时，同时检查所有 `lit/*` 子路径与 CSS、组件注册的 sideEffects，避免只外置一个包名。

验收分别覆盖“只用总包”“只用基础包”“同一应用混用”的实际页面，以及重复导入、主题切换和多语言初始化。不要直接全局替换 external 配置后发布。

### P2：把质量结果与发布提交关联

[CI](../.github/workflows/ci.yml) 已有多项检查，历史自评中的“类型检查缺失”“最小测试缺失”不应继续当作当前事实；但该工作流没有执行 lint。[release](../.github/workflows/release.yml) 在标签触发后校验根版本并构建，没有在配置内确认同一提交通过 CI，也没有检查打包后的安装结果。

工作流目前发布 tokens 和根总包。core、icons、i18n、utils 是否允许独立使用和发布，需要与 Changesets 及文档明确对齐；不能仅凭各包的 publishConfig 推断自动发布已覆盖全部包。

建议统一可复用的质量工作流，发布确认同一提交的检查结果；补 lint、exports 文件校验、独立消费者安装检查。记录版本、提交和产物信息。远端分支保护与 Trusted Publisher 是否启用，需要查看对应平台设置才能得出结论。

### P2：收敛构建入口和依赖方向

[整站组装脚本](../apps/portal/scripts/build-all.mjs) 先执行根 `pnpm run build`，而根 build 已包含 portal；随后再次执行 portal build。门户构建会清理自己的 dist，因此单独重建门户后必须重新组装 examples、Storybook 与图标资源。

建议保留一个明确的整站入口，仓库基础包、子站、静态资源组装分别只执行一次；门户 dev、整站产物预览与发布使用一致路径。先整理任务图再决定是否并行，不用新增一套构建工具。

原规划同时出现“页面 → ZDS”和“禁止页面直依赖 ZDS”，规则矛盾。建议确定：

1. 页面可以直接使用 ZDS 的基础组件和样式。
2. 基础组件不引用业务页面或内容平台。
3. 只有稳定的重复模式才进入 ZBC；ZBC 组合 ZDS，业务数据请求、业务状态和埋点仍在页面或业务应用。

这与[现有三场景准入规则](./markdown/zbc-playbook.md)基本一致。后续用 lint/依赖图检查真实违规方向，而不是强制所有页面经过尚未存在的组合层。

架构资料本身也需要单一数据来源：[architecture-data.ts](../apps/portal/src/architecture-data.ts) 中的 `archNodes`、`archFlows` 与 `panorama.ts` 的硬编码 SVG 独立维护，已有 `lp/campaign`、`obs/observability` 等不同节点标识。后续应统一节点、连线、状态、证据日期和文档链接，再从同一份数据生成图与文字说明，避免改了描述却遗漏图表。本次保留原图并直接修正展示文案，未重构图形生成器。

### P3：按真实页面需求建设 Atlas 和运行能力

当前仓库没有 Atlas、内容 API 或渲染核心的实现。先做一个具体页面的数据到组件原型，确认需求成立，再扩展为内容平台。

最小契约应包含内容数据版本、允许使用的组件名称、属性校验、未知组件的回退、旧数据的迁移和报错定位。内容平台负责编辑与内容发布，页面应用负责渲染与业务行为，站点部署系统负责缓存、监控和回滚。

SSR/Edge 应由实际页面的 SEO、首屏性能和动态需求决定。多区域缓存、灰度、错误聚合和转化分析不应作为每个基础组件的职责。先建立测量基线，再设性能和效率目标；原规划的提效百分比不是实测结果。

## 方案选择

| 方案 | 适用条件 | 取舍 |
| --- | --- | --- |
| A：先稳定总包，基础包同步修正契约 | 当前主要通过总包接入，团队规模与应用需求有限 | 改动较小；按组件接入暂时受限，必须与文档一致 |
| B：总包便捷接入 + 基础包完整契约（推荐） | 既要快速接入，也有减少体积、跨应用复用需求 | 保留现有结构；需要认真维护多入口、类型、依赖与消费者验证 |
| C：立即建设 Atlas、ZBC 与全套运行平台 | 已有明确业务场景、平台责任人和持续投入 | 工作量大，当前证据不足；容易先增加层级，再寻找用途 |

推荐 B，但分阶段落地：先修包契约与消费者验证，再统一运行依赖与发布，然后整理构建，最后用真实页面验证组合层和 Atlas。

## 落地顺序与风险控制

| 批次 | 结果 | 验收与兼容 |
| --- | --- | --- |
| 1 | exports、类型与样式对应真实文件 | 临时项目从 pack 产物安装；已有总包接入保持可用；移除公共路径按版本策略处理 |
| 2 | npm/CDN 入口和运行依赖明确 | 验证各接入组合；保留固定版本的旧 CDN 产物，消费者可切回已验证版本 |
| 3 | 同一提交通过检查后才发布，整站单次组装 | 加 lint 与包检查；从全新检出构建，验证所有页面和资源路径 |
| 4 | 一个内容页面验证数据契约与组件映射 | 只在示例或独立页面试用；出错可回退固定内容和已有页面实现 |

## 第一批实施结果

用户在展示和评估后授权“继续”，已落实方案 B 的包契约、混用可靠性、发布检查配置与整站构建修复。

| 范围 | 当前结果 |
| --- | --- |
| core | 总入口与十个组件子路径均生成 ESM/CJS、共享声明类型；补 dropdown 导出和公共样式 |
| utils | 生成实际 JavaScript/CJS 与声明，修复子路径和 NodeNext 类型解析 |
| i18n / icons | CommonJS 入口使用 `.cjs`；图标保留 UMD；声明集中生成 |
| 依赖与注册 | 基础包 Lit 范围统一，core/i18n/utils 外置 Lit 全部子路径；构建顺序反映真实基础包依赖；已有构造器可复用 |
| 多语言 | 模块初始化复用监听，混用时同步语言；DOM 初始化复用观察器，清理后支持重新初始化 |
| 包验证 | `packages:check` 校验六包文件；`packages:test` 从 pack 产物独立安装，覆盖 ESM/CJS、动态图标、混用两种顺序、严格 bundler/NodeNext 类型和 Vite 生产样式 |
| 发布配置 | CI 新增 lint、总包构建和消费者检查；标签发布依赖同一提交的可复用 CI |
| 整站构建 | 去掉重复门户构建；用一个入口构建并组装子站资源 |
| 文档生成 | 新版 AI 使用页成为门户模板；移除机器说明中的逐日时间变化，重复生成保持一致 |
| Storybook 冒烟 | 静态测试服务器保留 `.html` 路径，修复 iframe 被重定向至 404 的问题 |

总包与图标包仍保留内置 Lit，便于兼容既有 CDN 使用。混用可靠性修复不等于已经消除全部运行副本，npm/CDN 入口完全拆分仍是后续工作。图形与文字的单一数据来源、基础包独立发布策略、Atlas 原型和业务站点运行能力也尚未实施。

本次验证结果追加于 [验收记录](../ui-review/20261117/验收记录.md)。没有创建 Git 提交、运行远端发布或修改现网；远端 CI 和平台保护设置不属于已验证结果。

最终本地验收：六包 79 个文件声明通过；294 项组件测试、79 个 Storybook 渲染测试通过；全仓类型与 lint、样式检查、账户示例检查、整站构建通过。文档使用当前工作区的临时索引快照运行原 `docs:check`，确认重新生成无漂移，实际 Git 暂存区未修改。独立消费者的生产页面按钮、SVG、公共样式及英语到日语切换通过，架构页开发与生产模式的三种视口均无运行错误或 HTTP 资源错误。Storybook 仍会输出既有无障碍提示，渲染通过不等于完整无障碍验收。

## 全栈架构全景修订（2026-11-17）

用户否决原先只围绕前端的分类，并批准中文全栈蓝图后，ZDS-04 提前实施。范围为数字商业平台架构门户，Atlas 与 atlas-docs 只读；本次不建设实际后端、数据库或云资源。

### 已纠正的事实与分类

- 应用按完整任务分为品牌与内容门户、电商店面、营销活动中心、会员中心、帮助与售后门户、运营工作台。主页、商品详情、文章、落地页、帮助页、账户页与购物车是内部页面类型；手机/桌面是渠道。
- 多站点是独立访问入口与配置边界。例如品牌 A 欧洲店面与日本店面复用电商应用，却分别拥有域名、内容、主题、语言/币种、店铺、发布版本与 homeRegion。目标组织→品牌→站点；当前 site code 不等于完整集团模型或租户隔离。
- 同级 Atlas 已有 Admin、Builder、Java API、Preview、Publisher、Web/CLI 与 Schema、Runtime、客户端和管理 UI 库；消费者身份、会员权益、工单和完整营销规则未有实施证据。Atlas Account 不解释为消费者会员。
- 当前 API 主配置 PostgreSQL/Supabase，H2 保留迁移配置；README 的 H2→MySQL 说明过时。
- `PagePublishService` 回滚切历史内容指针并清草稿，不生成新版本。Publisher 实际先标记 LIVE，再渲染并写本地 dist，文件顶部注释顺序过时。库内事务不保证文件/S3/CDN 一致。
- Shopify 是商品、价格、库存、客户、订单、支付和履约权威；平台只持有店铺映射与必要投影。ERP/CRM/仓储/财务维持外部边界。

### 页面与模型

[统一数据](../apps/portal/src/architecture-data.ts) 包含七层的 39 个模块、4 项横切治理、217 项子能力，分别登记契约、数据、部署、证据和六场景。实现状态、验证状态、部署状态独立。当前资料核对日期固定为 2026-11-17，不随访问日期改变。

五视图为分层全景、依赖与调用、数据归属、区域部署、设计与验证。分层默认展开；点击模块阅读职责、功能、上下游、输入输出、数据归属、故障边界与证据。关系区分源码现状与目标、代码依赖与同步/事件/产物；全部模块登记上下游。SVG 仅绘制关系线，ResizeObserver + 单次 animation frame 更新；窄屏保留完整文字关系列表。

目标领域只依赖自身规则和纯类型，适配器实现内层端口；当前 Java Service→Repository/持久实体耦合与 Runtime 相对源码导入标为演进缺口。ZDS 在体验层，业务界面可直接使用基础库；稳定复用后再建立组合。

目标发布固定内容、主题、Runtime、配置四版本，经 Outbox/幂等 Worker 构建不可变产物、校验、条件激活、CDN 确认；失败保留旧发布。完整 release 回滚与当前内容指针回滚分开；旧版本无完整产物不能承诺即时回滚。

部署采用全球非敏感控制面、公开 CDN 与区域业务面，homeRegion 归属写入；建议 Java 模块化部署、Preview/Publisher 独立资源、区域 PostgreSQL/Supabase/S3 和按需托管队列，不默认引入 Kafka/Kubernetes/服务网格。生产拓扑、授权隔离、区域驻留与跨区灾备未核实。

### 本轮验证与限制

新增 `pnpm --filter @aiyazone/portal run check:architecture` 检查 ID、引用、关系、日期、三类状态、事实证据、所属模块功能、全部模块上下游，以及真实 core 导出是否完整列入 ZDS 详情。临时编译产物在系统临时目录清理。旧结构先被检查拒绝，统一数据随后通过；门户 TypeScript/Vite、仓库 lint 与整站组装通过。

浏览器在 1440×900、768×1024、390×844 验证 43 个模块选择、详情阅读/返回焦点、五视图、六场景的关系类型与现状/目标组合；无页面横向溢出，移动端关系线关闭。桌面七层与治理首屏完整可见，图面约 574px，底边约 876px。原生 Enter/Tab/Space 选择与焦点一致。

截图与可复验的浏览器断言位于 [本轮验收目录](../output/architecture-20261117/)。历史完整图、评分和升级设想保留在 `panorama-history.ts` 与页面末尾折叠区，明确标注历史、未重新核实；不参与当前数据生成。

构建仍有既有图标静态/动态导入和 Storybook 大块提示；不影响通过。可靠性分级均为待业务确认、待压测/演练的建议，容量参数未取数时直接显示未取数。门户验证不能证明生产 SLA、灾备或整个平台成熟，也没有创建提交、推送或发布。
