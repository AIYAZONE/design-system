# ZBC 准入与 AI 页面生成 Playbook

> ZBC（Zone Business Components，业务组件层）定位：**最薄的组合层**。本文回答两个问题——什么时候值得把一个业务模式沉淀为 ZBC；AI 如何按 ZDS 规范生成业务页面。

## 一、定位与边界

```
Business Layer（业务页面）        ← AI 按本 Playbook 现生成
Domain Capability（ZBC 业务组件）  ← 仅沉淀高频复用模式，保持最薄
Design System（ZDS 基础组件）     ← 唯一的"零件"来源
Design Tokens（--zone-* 令牌）    ← 唯一的"样式词汇"
```

- ZBC **必须**由 ZDS 基础组件 + `--zone-*` 令牌组合而成，禁止重写按钮/弹窗/下拉等原语的内部实现；
- 业务逻辑（数据请求、状态管理、埋点）**不进入** ZBC，ZBC 只负责交互模式与展示结构；
- 未达到准入条件的业务模式，由 AI 按第四节的流程现场生成，不预制。

## 二、准入规则（三条同时满足才立项）

1. **复用度**：同一交互/展示模式在 ≥3 个业务场景中实际出现（不是"将来可能用"）；
2. **稳定性**：模式的行为契约已稳定（API 形状不再每周变）；
3. **可抽象**：能用「基础组件 + 令牌」完整表达，不依赖特定业务数据结构。

不满足 → 留在业务页面，由 AI 生成；满足 → 走第五节的立项流程。

## 三、API 形状约定

| 维度 | 约定 |
|------|------|
| 命名 | 标签 `zone-biz-<name>`，类 `ZoneBiz<Name>`，文件 `packages/biz/src/components/<name>/` |
| 受控/非受控 | 双模式：`value` + `zone-biz-change` 事件；同时支持 `default-value` 非受控 |
| 事件 | 一律 `zone-biz-<event>` custom event，`detail` 携带结构化数据，`bubbles: true, composed: true` |
| 数据 | 通过属性传**纯数据**（JSON-able），不传业务 store/服务实例 |
| 样式钩子 | 只暴露 `--zone-biz-*` CSS 变量，且值默认引用 `--zone-*` 令牌 |
| 插槽 | 结构性扩展点用 `<slot>`，内容定制优先用属性 |
| 文档 | 类注释必须含 `@summary` 与 `@cssproperty`（AI 文档生成器依赖它们） |
| 测试 | 每个 ZBC 至少：交互用例 + a11y 断言 + 键盘导航用例 |

## 四、AI 页面生成 Playbook

生成业务页面时的固定流程（提示词模板见 `/ai-usage.html`）：

1. **令牌先行**：布局与配色全部使用 `--zone-*`，不发明新值；
2. **组件优先**：交互元素从 ZDS 十组件中选择，缺失时按第五节判断是否值得沉淀 ZBC；
3. **组合生成**：页面 = ZDS 组件 + 少量胶水布局代码（flex/grid + 令牌）；
4. **验收自检**：跑 `/ai-usage.html` 第六节的验收清单，全部通过才算完成；
5. **沉淀回路**：同一模式第 3 次出现时，停下来按第二节评估立项 ZBC，而不是第 4 次复制粘贴。

## 五、ZBC 立项流程

1. 在本文档附录登记：模式名称、出现的 3 个业务场景、API 草案；
2. 用 AI 按「API 形状约定」生成组件骨架 + 测试 + Storybook story；
3. 人工评审 API（重点：受控语义、事件 detail 结构、样式钩子边界）；
4. 合入 `packages/biz`，版本号独立演进；文档经 `pnpm docs:gen` 自动进入 API 索引与 `llms.txt`；
5. 全景图 Domain 层芯片同步登记（`apps/portal/src/main.ts`）。
